## 1. Общая структура

- В репозитории присутствуют **ветки микросервисов**.
- При создании нового микросервиса создаётся отдельная ветка **от `main`**.
- Каждая такая ветка является основной для кода своего микросервиса.
- Разработчики создают **feature‑ветки** от ветки целевого микросервиса.
- Когда фича готова – она вливается обратно в ветку микросервиса через **Pull Request (PR)**.
- **Релиз** – это обновление главной ветки `main`. После релиза **все** ветки микросервисов и активные feature‑ветки должны быть синхронизированы с `main`.

## 2. Соглашения по именованию веток

| Тип ветки    | Формат                                         | Пример                                            |
| ------------ | ---------------------------------------------- | ------------------------------------------------- |
| Микросервис  | `<ms-name>`                                    | `auth-service`, `twitch-service`                  |
| Feature      | `<ms-name>/feature/<task-number>-<short-desc>` | `auth-service/feature/1.5.1.1-login-and-register` |
| Hotfix (fix) | `<ms-name>/hotfix/<task-number>-<short-desc>`  | `auth-service/hotfix/1.5.1.1-login-and-register`  |

## 3. Правила работы с feature‑ветками

### 3.1 Создание ветки
- Всегда от актуальной ветки микросервиса (`<ms-name>`).
- Перед созданием выполнить `git pull origin <ms-name>`.
### 3.2 Разработка
- Коммиты должны быть атомарными и иметь осмысленные сообщения.
- Рекомендуется пушить feature‑ветку в удалённый репозиторий на раннем этапе для бэкапа и коллаборации.
### 3.3 Pull Request (PR)
- **Target:** ветка микросервиса (`<ms-name>`).
- **Требования к PR:**
  - Успешное прохождение CI.
  - Approve от тимлида.
  - Отсутствие конфликтов с target‑веткой.
## 4. Релизный процесс
Релизом считается **обновление ветки `main`**.
### 4.1 Подготовка релиза (для любого микросервиса)
1. Ветка микросервиса `<ms-name> должна быть полностью протестирована.
2. Создаётся PR из `<ms-name>` -> `main`.
3. PR проходит ревью и все проверки CI/CD.
4. После merge в `main` – версия микросервиса считается выпущенной.
5. Ветка микросервиса после PR продолжает жить.
### 4.2 Синхронизация после релиза
**Правило:** в течение 2 часов после обновления `main` все ветки микросервисов и открытые feature‑ветки должны быть синхронизированы.
